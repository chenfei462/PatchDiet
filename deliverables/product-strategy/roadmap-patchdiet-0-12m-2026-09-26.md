# PatchDiet 产品路线图更新（0-12 个月）

**日期**：2026-09-26
**类型**：路线图更新
**参与成员**：路径（路线图规划师）、数析（数据分析师）、瑞思（用户研究员）、竞析（竞品分析师）
**规划周期**：2026 Q4 - 2027 Q3

---

## 📌 TL;DR（执行摘要）

- **核心目标**：把 PatchDiet 从本地可运行的产品雏形，推进为可分发的可信工具，再推进为有团队价值与治理能力的商业产品。
- **关键决策**：三阶段节奏 —— **短期（0-3 月）可信发布与真实仓库验证** → **中期（3-6 月）分发扩张与团队价值验证** → **长期（6-12 月）商业化与治理能力**。
- **关键决策**：不追求功能数量扩张，而是**先用真实仓库验证与公开 benchmark 建立可信度**，再谈分发与商业化。
- **下一步**：npm 真实发布 + ≥ 20 个真实仓库验证 + 报告 reason code 升级，这三件事是后续一切的前置条件。

|------|------|----------|------|

| 一级 | Shrink 采纳率 | [待采集] | `[待采集]` |

| 二级 | shrink 运行成功率 | 3 个 fixture 全绿 | `Evidence`（fixture 级） |
| 二级 | 首次成功耗时 | [待采集] | `[待采集]` |
| 二级 | 测试命令耗时占比 | 已有采集字段（test duration），无数值 | `[待采集]` |
| 二级 | needs-human-review 候选占比 | 已有采集字段，无数值 | `[待采集]` |
| 护栏 | 源码出域事件 | 0（设计保证） | `Evidence`（契约级） |
| 护栏 | 分支重写事件 | 0（默认路径设计保证） | `Evidence`（契约级） |

**基线事实**
- Fixture：3 个（`ts-bloated-pr` / `python-agent-refactor` / `monorepo-scope-creep`），断言"保留行为 patch""默认保留测试文件""仅检查通过时移除"。
- 公开声称口径：4 files / 128 changed lines → 2 files / 32 changed lines（75%），`node --test` 仍通过。
- **限制**：`docs/benchmark.md` 明确声明**尚无**营销级公开 benchmark 数据集，现有示例应视为 smoke test。

**这对路线图的含义**：短期阶段的第一优先级**不是加功能，而是补基线**。没有真实仓库验证集，VRRS 无法被校准，也无法对外证明，后续所有分发与商业化动作都缺少说服力。

## 2. 用户反馈摘要（来自瑞思 · 用户研究员）

| Persona | 短期（0-3 月）最关心 | 中期（3-6 月）最关心 | 长期（6-12 月）最关心 |
|---------|----------------------|----------------------|------------------------|
| **P1 · Tech Lead / 技术负责人** | "能不能一键跑通，报告能不能说服我的 reviewer" | "团队里有多少人真的在用，效果能不能量化给上级看" | "能不能统一策略，能不能审计，出了问题谁负责" |
| **P2 · 平台 / DevEx 工程师** | "会不会上传源码，时间开销多大，失败会不会阻断 CI" | "能不能自托管，能不能接入我们的 runner，策略能不能下发" | "SSO/SAML、审计日志、保留策略、组织级管控" |
| **P3 · 独立开发者 / 开源维护者** | "零配置吗，免费吗，本地跑吗" | "IDE 里能不能直接用，结果能不能分享" | "有没有免费档，社区能不能看到效果" |

**核心 JTBD（横跨三阶段不变）**
> 当我的 AI agent 提交了一个测试通过、但过大或混入无关改动的 PR 时，我要在请人 review 之前把它变小，这样 reviewer 只需要看真正有行为变化的代码。

**关键诉求对路线图的直接约束**
1. **信任先于功能**（P1/P2 共同）：误删护栏与可回滚性必须在 P0 阶段完成，不能推迟。
2. **隐私是采购前提**（P2）：本地优先契约与自托管路线必须在长期阶段给出明确承诺。
3. **零摩擦是采纳关键**（P3）：零配置与免费公开仓库档必须从第一天可用。

## 3. 竞品动态（来自竞析 · 竞品分析师）

### 3.1 赛道演进方向

| 竞品类别 | 演进方向 | 对 PatchDiet 的影响 |
|----------|----------|---------------------|
| AI reviewer（Copilot / CodeRabbit / Greptile） | 持续朝"**更多、更智能的 review comments**"演进，赛道极度拥挤 | 说明"智能评论"位置已被占满，PatchDiet 必须走反向 |
| lint bot（reviewdog / Danger） | 稳定在"规则类问题自动化" | 与 PatchDiet 互补，不构成竞争 |
| PR workflow（Graphite） | 从事前拆分解决 PR 过大 | 与 PatchDiet 可共存（事前 vs 事后） |

### 3.2 时间压力判断

| 压力来源 | 说明 | 对路线图的含义 |
|----------|------|----------------|
| 平台向上覆盖 | GitHub Copilot 有能力增加 diff 缩减；CodeRabbit 可加 cleanup patch | **P0 必须在 0-3 个月内完成 npm 发布与可信度建设**，先用真实用户与案例占位 |
| 计费向用量迁移 | 平台开始对 code review runs 计费，团队更关注每步价值 | 可借势强调"缩减 review surface"的 ROI |
| 隐私合规需求 | 竞品多为云端 SaaS，本地优先留出空间 | 长期阶段的自托管与 SSO 是企业市场的入场券 |

**关键结论（`Inference`）**：PatchDiet 的护城河不在功能，而在**可信度**。功能可被平台复制，但"本地优先 + 不上传源码 + 测试验证 + 可审计收据"这套组合需要平台放弃自身商业叙事才能跟进。因此路线图的排序原则是 —— **先建立可信度资产（真实仓库验证 + 公开 benchmark），再做分发扩张，最后做商业化**。

## 6. 利益相关者沟通要点

### 6.1 高管视图

1. **市场机会**：AI coding agent 大幅提升了 PR 生成速度，但把负担转移到了人工审查环节。PatchDiet 不参与"更聪明的审查工具"竞争，而是解决"审查面过载"这个相反的、目前几乎无人占据的问题。
2. **差异化护城河**：不是功能，而是**可信度组合** —— 本地优先、不上传源码、测试验证、可审计收据。平台若要复制，需要放弃其云端商业叙事。
3. **投入产出**：主要投入是工程时间与真实仓库验证的数据工作；最大回报是占住一个可被定义的新品类词，而非在红海中争夺份额。
4. **风险与不确定性**：平台级玩家向上覆盖是真实风险；同时本次分析**缺少可引用的行业一手数据**，市场规模判断目前建立在推断而非证据之上。
5. **需要什么决策**：是否批准"先做可信度、后做商业化"的排序，接受短期不追求用户数增长。
6. **明确不做什么**：不做 AI reviewer，不替代 CI，不做云代码上传分析 —— 这些是定位纪律，不是能力限制。

### 6.2 工程视图

1. **技术债优先级**：报告 reason code 体系（`PD-04`）是当前最值得投入的内部改造，它同时改善可解释性、可测试性与未来的指标采集。
2. **架构演进路径**：hunk/file 级 → 依赖感知分组（`PD-15`）→ AST atoms（`PD-16`）。进阶必须先保证性能预算不被突破。
3. **性能预算**：中位 cleanup ≤ 60 秒、CI 步骤 ≤ 总时长 20%、重复运行 ≤ 首次 30%。这三条是硬约束，任何精度提升不得以突破它们为代价。
4. **测试策略**：现有 3 个 fixture 只能算 smoke test。短期必须把真实仓库验证集（`PD-03`）建成可回归的测试资产，并纳入 CI。
5. **发布工程**：npm trusted publishing + provenance + `smoke:release` 全链路门禁（`PD-01`/`PD-02`）是短期最关键的工程交付，任何失败必须阻断发布。
6. **并发与缓存**：worktree 变更必须串行、测试检查可并发（`performance.max_parallel_worktrees`）；测试结果缓存的正确性验证优先于命中率优化。
7. **集成面**：GitHub Action 的评论幂等性（`PD-07`）是生产可用性的核心风险点，需重点测试重复触发场景。

### 6.3 设计视图

1. **报告是产品本身**：用户对 PatchDiet 的信任来自报告，而不是 CLI 输出。报告必须让人**在 3 秒内**理解省了多少、是否安全。
2. **错误与失败状态是信任的关键时刻**：误删被拦下时，不能让用户感到"工具差点害我"，而要让用户感到"工具保护了我"。失败状态需要正面叙事。
3. **可解释性设计**：reason code（无关文件 / 生成物 / 格式化噪音 / 无引用代码 / 需人工判断）需要一套清晰、可扫读的视觉语言，而不是纯文本标签。
4. **Diet Card 与 badge 的定位**：它们是**分享动机**而非装饰。设计目标应让卡片在不看正文的情况下也能被理解。
5. **IDE 内交互边界**：VS Code 扩展的 dry-run 必须是安全的默认体验 —— 让用户在应用前完整看到结果，且随时可放弃。
6. **隐私感知设计**：`doctor` 的隐私状态自检需要一眼可读，让用户直观确认"我的代码没有出去"。
7. **信息密度纪律**：背景是用户抱怨"工具给我更多东西看"。报告的信息层级必须服务于"减少认知负担"这一产品承诺。
